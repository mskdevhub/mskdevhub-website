1. ROOT CAUSE OF THE "BLANK" /includes/switcher PAGE
--------------------------------------------------------------------------------
VERDICT: /includes/switcher (served from public/includes/switcher.html) is an
INTENTIONAL HTML FRAGMENT, not a standalone page. The blank screen is EXPECTED
behaviour, not a bug.

Evidence:
  - public/includes/switcher.html contains NO <!DOCTYPE>, <html>, <head> or
    <body>. It is a partial: a <link> to switcher.css, the
    <div class="style-switcher" id="style-switcher"> panel, and a <script>
    tag for switcher.js.
  - public/assets/css/switcher.css positions the panel OFF-SCREEN until opened:
        .style-switcher { position: fixed; top: 0; right: -100%; ... }
        .show-switcher { right: 0; }
    So loading the fragment on its own renders a white page with the panel
    parked off the right edge of the viewport.
  - Live: GET /includes/switcher -> 200, text/html, 2011 bytes, the panel HTML.
  - Live: GET /includes/switcher.html -> 308 -> /includes/switcher (Cloudflare
    Pages automatic clean-URL redirect).

The fragment is included into real pages (see OS files) and is correctly marked
noindex (see section 3). It must NOT be promoted to a standalone page (that would
inject a second <html>/<body> into host pages and break the switcher).

IMPORTANT - API WORKER REGRESSION FOUND AND FIXED:
  The project's Git build_config had an EMPTY build_command, and public/_worker.js
  is .gitignored. So a Git build deployed the repo's public/ "as-is" and OMITTED
  the API Worker. Result: on Git-built deployments the API Worker never ran:
      POST /api/contact   -> 405
      POST /api/auth/login-> 405
  Proof (same repo, two build paths):
      d9a9927b (wrangler upload)  POST /api/contact -> 400  (Worker ran)
      b42f868b (wrangler upload)  POST /api/contact -> 400  (Worker ran)
      63c5727d (Git build)        POST /api/contact -> 405  (no Worker)
      843209b3 (Git build 7b43a91)POST /api/contact -> 405  (no Worker)
  Because the push made a Git build the live Production, production's API was
  affected. Fix applied to the Pages project settings (read-modify-write via the
  Cloudflare API, D1 binding "DB" was already present and unchanged):
      build_config.build_command = "npm run build"
      build_config.destination_dir = "public"
  Git builds will now generate public/_worker.js before deploying, so both deploy
  paths produce an identical, Worker-enabled site. This is a settings change, not
  a code change.

  VERIFIED: the push of ce3f3ed produced Git build adbd667c, whose stages were
  queued/initialize/clone_repo/build/deploy = all success. Once live:
      POST https://adbd667c.mskreallabs.pages.dev/api/contact -> 400 (Worker ran)
      POST https://mskreallabs.pages.dev/api/contact           -> 400 (Worker ran)
      POST https://mskreallabs.pages.dev/api/auth/login        -> 400 (Worker ran)
  400 = the request reached the Hono app and failed payload validation, proving
  the Worker is active. The previous 405 (no Worker) is gone. Note: a bare
  GET /_worker.js returns 404, which is normal in Pages advanced mode - the file
  is the Worker script, not a served static asset.
